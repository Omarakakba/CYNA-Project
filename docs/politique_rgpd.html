3. Base légale des traitements

Conformément à l'article 6 du RGPD, les traitements reposent sur les bases légales suivantes :

  • Art. 6(1)(a) — Consentement : acceptation obligatoire des CGU lors de l'inscription (case à cocher, non pré-cochée). Le consentement est traçable par le champ cgu_accepted (booléen) en base de données.

  • Art. 6(1)(f) — Intérêt légitime : sécurisation de la plateforme (rate limiting, logs de connexion, protection CSRF/XSS).

5. Mesures techniques de sécurité

Conformément à l'article 32 RGPD (sécurité du traitement), les mesures suivantes sont implémentées :

5.1 Protection des mots de passe

  • Algorithme : bcrypt via password_hash($password, PASSWORD_BCRYPT, ['cost' => 12])
  • Vérification : password_verify() — résistant aux attaques de timing
  • Les mots de passe en clair ne sont jamais stockés ni loggués

5.2 Protection contre les injections SQL

  • Toutes les requêtes utilisent des requêtes préparées PDO avec execute([])
  • Aucune concaténation directe de variables dans les requêtes SQL
  • Exemple : $stmt = $db->prepare('SELECT * FROM user WHERE email = ?'); $stmt->execute([$email]);

5.3 Protection CSRF

  • Tous les formulaires POST incluent un token CSRF : bin2hex(random_bytes(32))
  • Validation par hash_equals() — résistant aux attaques de timing
  • Token stocké en session, invalidé après utilisation

5.4 Protection XSS

  • Toutes les sorties HTML passent par htmlspecialchars($val, ENT_QUOTES, 'UTF-8')
  • En-têtes de sécurité : X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Content-Security-Policy

5.5 Rate limiting (anti-brute-force)

  • Maximum 5 tentatives de connexion par IP sur 15 minutes
  • Stocké en base de données (table rate_limit) — nettoyage automatique après expiration
  • Alertes Grafana si ≥ 5 tentatives en 5 minutes (niveau Critical)

5.6 Tokens de session

  • Régénération de l'ID de session après chaque connexion : session_regenerate_id(true)
  • Cookie "remember me" : token aléatoire (32 octets) stocké hashé en SHA-256 en BDD
  • Attributs du cookie : httponly: true, samesite: Lax

6. Anonymisation des données lors de la suppression

Lors de la suppression d'un compte (art. 17 RGPD), le processus est le suivant :

  1. Les adresses de facturation sont supprimées en cascade (ON DELETE CASCADE)
  2. Les commandes sont conservées (obligations comptables — art. L123-22 Code de commerce) mais anonymisées : user_id = NULL (colonne NULLABLE avec ON DELETE SET NULL)
  3. Le compte utilisateur est supprimé (DELETE FROM user WHERE id = ?)
  4. Le cookie remember_me est supprimé côté client et le token invalidé en BDD
Ce choix de conception — order.user_id NULLABLE — est une décision délibérée prise dès la phase de modélisation pour concilier le droit à l'effacement (art. 17) avec les obligations légales de conservation des données de transaction.
